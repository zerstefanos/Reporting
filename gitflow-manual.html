01 Τι είναι το Git & Γιατί το Χρειαζόμαστε

Η βάση — τι κάνει το Git και τι πρόβλημα λύνει στην ομαδική ανάπτυξη.

🤔 Φαντάσου το εξής

Έχεις ένα αρχείο sales_etl.sql και δουλεύεις σε αυτό με 3 συναδέλφους ταυτόχρονα. Χωρίς Git, ο ένας κάνει override τον άλλο. Με Git, κάθε αλλαγή καταγράφεται, η ιστορία διατηρείται, και μπορείς να επιστρέψεις σε οποιοδήποτε σημείο στο παρελθόν.

📸

Snapshot

Κάθε commit είναι μια "φωτογραφία" του κώδικα σε εκείνη τη στιγμή. Μπορείς πάντα να γυρίσεις πίσω.

🌿

Branch (Κλάδος)

Δουλεύεις απομονωμένα. Ό,τι κάνεις σε ένα branch δεν επηρεάζει τους άλλους μέχρι να κάνεις merge.

🔀

Merge

Ενώνεις δύο branches. Αν υπάρχουν conflicting αλλαγές, το Git σε ρωτάει τι να κρατήσει.

☁️

Remote version control repository (π.χ. Azure DevOps, GitLab, GitHub)

Ο "κεντρικός server" που κρατάει τον κώδικα. Κάνεις push για να ανεβάσεις, pull για να κατεβάσεις.

💡
Gitflow = Στρατηγική Το Gitflow δεν είναι εργαλείο — είναι μια συμφωνία για το πώς θα χρησιμοποιούμε το Git. Ορίζει ποια branches υπάρχουν, από πού ξεκινάνε και πού καταλήγουν.

02 Τα 5 Branches & Ο Ρόλος τους

Κάθε branch έχει έναν συγκεκριμένο σκοπό. Δεν τα αγγίζουμε "όπως μας βολεύει".

🔴 main

Ο κώδικας που τρέχει LIVE στην παραγωγή. Ποτέ δεν αγγίζεται απευθείας. Μόνο δέχεται merges από release ή hotfix.

production-ready μόνο

🟢 develop

Ο "κόμβος" ανάπτυξης. Εδώ μαζεύονται όλα τα features. Ποτέ δεν γράφουμε απευθείας — δεχόμαστε μόνο merges από features, releases, hotfixes.

integration branch

🟣 feature/*

Εδώ γράφουμε κώδικα. Ξεκινά από το develop, τελειώνει στο develop. Κάθε task = ένα feature branch.

π.χ. feature/sales-etl ξεκινά από: develop

🟠 release/*

Προετοιμασία για deployment. Μόνο bugfixes, όχι νέα features. Πηγαίνει για UAT testing.

π.χ. release/v1.0 ξεκινά από: develop

🔴 hotfix/*

Επείγουσα διόρθωση στην παραγωγή. Ξεκινά από το main, γυρίζει στο main ΚΑΙ στο develop.

π.χ. hotfix/fix-filter ξεκινά από: main
🔢
Σημείωση: Τι σημαίνουν οι αριθμοί στα releases (v1.0, v1.1, v1.0.1…)

Οι αριθμοί λειτουργούν ως απλό σύστημα αναφοράς για να ξέρει η ομάδα τι ανέβηκε και πότε. Η λογική είναι:

v1.0  →  Πρώτο release στην παραγωγή
v1.1  →  Νέο release με features (ο μεσαίος αριθμός αυξάνεται)
v1.2  →  Επόμενο release με features
v1.0.1 →  Hotfix του release v1.0 (ο τελευταίος αριθμός αυξάνεται)
v1.1.1 →  Hotfix του release v1.1

Σύνοψη: ο μεσαίος αριθμός αυξάνεται για κάθε νέο release, ο τελευταίος για κάθε hotfix πάνω σε αυτό.

03 Τα 3 Περιβάλλοντα: DEV → UAT → PROD

Ο κώδικας δεν πηγαίνει ποτέ κατευθείαν στην παραγωγή. Περνά από 3 στάδια ελέγχου.

👨‍💻

DEV

Το περιβάλλον του developer. Εδώ γράφεις και δοκιμάζεις. Αντιστοιχεί στο feature/* branch.

→
🧪

UAT

User Acceptance Testing. Οι business users ελέγχουν ότι λειτουργεί σωστά. Αντιστοιχεί στο release/* branch.

→
🚀

PRODUCTION

Live περιβάλλον. Αγγίζεται μόνο μετά από έγκριση UAT. Αντιστοιχεί στο main branch.

✅
Γιατί 3 περιβάλλοντα; Αν κάτι "σπάσει" στο DEV, δεν επηρεάζει τους χρήστες. Αν κάτι δεν αρέσει στο UAT, δεν φτάνει στην παραγωγή. Τα στρώματα ελέγχου προστατεύουν το LIVE σύστημα.

04 Το Πλήρες Διάγραμμα Gitflow

Η οπτική αναπαράσταση όλων των branches και πώς συνδέονται μεταξύ τους.

📌
Πώς να διαβάσεις το διάγραμμα Οι γραμμές αριστερά→δεξιά δείχνουν την πρόοδο του χρόνου. Κάθε κύκλος = ένα commit. Οι διακεκομμένες γραμμές = merges μεταξύ branches. Τα χρυσά tags (v1.0, v1.0.1) δείχνουν releases στην παραγωγή.

05 Τα 5 Βασικά Σενάρια

Βήμα-βήμα οδηγίες για κάθε περίπτωση που θα συναντήσεις στην καθημερινότητα.

📦 Καθημερινή Ανάπτυξη — Feature Branch

Όταν ξεκινάς μια νέα εργασία (π.χ. ένα νέο ETL Job ή SQL transformation).

  • 1
    Πήγαινε στο develop
    Πάντα ξεκινάς από εκεί
  • 2
    Ενημέρωσε τον τοπικό κώδικα
    Κατέβασε τις τελευταίες αλλαγές
  • 3
    Δημιούργησε το feature branch
    Δουλεύεις απομονωμένος
  • 4
    Γράψε κώδικα & κάνε commits
    Μικρά, συχνά, descriptive commits
  • 5
    Push & Pull Request
    Ανέβασε και ζήτα code review
  • 6
    Merge & Καθαρισμός
    Μετά την έγκριση, διέγραψε το feature branch
Terminal — Scenario 1: Feature
# Βήμα 1 & 2: Πήγαινε στο develop και ενημερώσου
git checkout develop
git pull origin develop

# Βήμα 3: Δημιούργησε το feature branch
git checkout -b feature/sales-task

# Βήμα 4: Δούλεψε... και κάνε commits
git add .
git commit -m "feat: add sales transformation logic"
git commit -m "fix: correct date filter in query"

# Βήμα 5: Push στο remote
git push origin feature/sales-task
# → Πήγαινε στο GitHub/GitLab και άνοιξε Pull Request

# Βήμα 6: Μετά την έγκριση, καθάρισε τοπικά
git checkout develop
git branch -d feature/sales-task
✅
Καλή πρακτική: Ένα feature branch = μία εργασία. Μην βάζεις άσχετα πράγματα στο ίδιο branch.

🧪 Προετοιμασία Release & Bug στο UAT

Όταν μαζεύεις τα features για να τα πας για έλεγχο. Εδώ δεν υπάρχουν νέα features — μόνο bugfixes.

  • 1
    Πήγαινε στο develop & ενημερώσου
    Κατέβασε όλα τα merged features
  • 2
    Δημιούργησε το release branch
    Αυτό θα πάει για UAT testing
  • 3
    Βρέθηκε bug στο UAT; Διόρθωσε εδώ
    Απευθείας στο release branch — ΜΟΝΟ bugfixes
  • 4
    Push & πέρνα για re-testing
    Στείλε ξανά στο UAT για επαλήθευση
Terminal — Σενάριο 2: Release & UAT
# Βήμα 1: Ξεκίνα από το ενημερωμένο develop
git checkout develop
git pull origin develop

# Βήμα 2: Δημιούργησε release branch
git checkout -b release/v1.0
git push origin release/v1.0
# → Deploy στο UAT περιβάλλον

# Βήμα 3: Βρέθηκε bug στο UAT — διόρθωσε απευθείας
#   (π.χ. φίλτρο λάθος στο SQL)
git add .
git commit -m "fix: aggregation error found in UAT"
git push origin release/v1.0
# → Ξαναστείλε για UAT re-test
⚠️
Κανόνας: Στο release branch ΔΕΝ βάζεις νέα features. Μόνο bugfixes, docs, και μικρές διορθώσεις. Αν θέλεις νέο feature, πηγαίνει στο επόμενο release.

🚀 Ολοκλήρωση Release — Deployment στην Παραγωγή

Το UAT έδωσε "ΟΚ". Πάμε παραγωγή! Αυτό είναι το πιο κρίσιμο βήμα — ακολούθα με ακρίβεια.

  • 1
    Merge στο main (Live)
    Αυτό βάζει τον κώδικα στην παραγωγή
  • 2
    Tag (Σφραγίδα της έκδοσης)
    Σηματοδοτεί το release — π.χ. v1.0
  • 3
    Back-merge στο develop ⚠️ ΚΡΙΣΙΜΟ
    Οι bugfixes του release πρέπει να πάνε και στο develop!
  • 4
    Διαγραφή release branch
    Δεν το χρειαζόμαστε πλέον
Terminal — Σενάριο 3: Deployment
# Βήμα 1: Merge στο main (Παραγωγή)
git checkout main
git merge release/v1.0

# Βήμα 2: Ταγκάρισε την έκδοση
git tag -a v1.0 -m "Production Release v1.0"
git push origin main --tags

# Βήμα 3: ΚΡΙΣΙΜΟ — Back-merge στο develop
#   (αν παραλείψεις αυτό, τα bugfixes θα χαθούν!)
git checkout develop
git merge release/v1.0
git push origin develop

# Βήμα 4: Διέγραψε το release branch
git branch -d release/v1.0
git push origin --delete release/v1.0
🚨
Το πιο συχνό λάθος: Να ξεχάσεις το back-merge στο develop. Τότε, τα bugfixes που διόρθωσες στο UAT θα ξαναεμφανιστούν στο επόμενο release!

⚔️ Συγχρονισμός & Επίλυση Conflicts

Ένας συνάδελφος έκανε merge στο develop πριν από σένα. Τώρα υπάρχουν "συγκρουόμενες" αλλαγές.

  • 1
    Ενημέρωσε το τοπικό develop
    Κατέβασε τις αλλαγές του συναδέλφου
  • 2
    Πήγαινε στο feature σου & κάνε merge develop
    Ενσωμάτωσε τις αλλαγές του στο δικό σου branch
  • 3
    Επίλυσε τα conflicts
    Ανοίγεις τα αρχεία, διαλέγεις τι να κρατήσεις
  • 4
    Commit & Push
    Ολοκλήρωσε και ανέβασε
Terminal — Σενάριο 4: Επίλυση Conflicts
# Βήμα 1: Ενημέρωσε το τοπικό develop
git checkout develop
git pull origin develop

# Βήμα 2: Πήγαινε στο feature σου
git checkout feature/my-task
git merge develop
# → Θα δεις κάτι σαν: CONFLICT (content): Merge conflict in sales.sql

# Βήμα 3: Άνοιξε το αρχείο — θα δεις:
# <<<<<<< HEAD   (ο δικός σου κώδικας)
# SELECT * FROM sales WHERE date > '2024-01-01'
# =======
# SELECT * FROM sales WHERE region = 'EU'   (συνάδελφος)
# >>>>>>> develop
#
# Διόρθωσε — κράτα το σωστό, σβήσε τα <<< === >>>

# Βήμα 4: Ολοκλήρωσε το merge
git add .
git commit -m "chore: resolve conflicts with develop"
git push origin feature/my-task
💡
Συμβουλή: Κάνε merge develop στο feature branch σου συχνά (κάθε μέρα ή δύο). Όσο πιο συχνά, τόσο μικρότερα τα conflicts.

🔥 Hotfix — Επείγουσα Διόρθωση στην Παραγωγή

Βρέθηκε κρίσιμο bug στο LIVE σύστημα και πρέπει να διορθωθεί τώρα. Ξεκινάς από το main, ΟΧΙ από το develop.

  • 1
    Ξεκίνα από το main (ΟΧΙ develop!)
    Θέλεις τον κώδικα που είναι ακριβώς στην παραγωγή
  • 2
    Δημιούργησε hotfix branch
    Διόρθωσε μόνο αυτό που καίει
  • 3
    Merge & Tag στο main
    Ανέβασε στην παραγωγή με νέο version tag
  • 4
    Back-merge στο develop ⚠️ ΚΡΙΣΙΜΟ
    Αλλιώς το bug θα ξαναεμφανιστεί!
  • 5
    Back-merge στο ενεργό release (αν υπάρχει)
    Αν υπάρχει release/v1.1 ανοιχτό, κάνε merge και εκεί
Terminal — Scenario 5: Hotfix
# Βήμα 1 & 2: Ξεκίνα από main, δημιούργησε hotfix
git checkout main
git checkout -b hotfix/fix-prod-filter

# Βήμα 3: Διόρθωσε & commit (μόνο αυτό που καίει!)
git add .
git commit -m "fix: production critical filter correction"

# Βήμα 4: Merge & Tag στο main
git checkout main
git merge hotfix/fix-prod-filter
git tag -a v1.0.1 -m "Hotfix for filter bug"
git push origin main --tags

# Βήμα 5: ΚΡΙΣΙΜΟ — Back-merge στο develop
git checkout develop
git merge hotfix/fix-prod-filter
git push origin develop

# Βήμα 6: Αν υπάρχει ενεργό release branch, merge εκεί επίσης
git checkout release/v1.1
git merge hotfix/fix-prod-filter
git push origin release/v1.1

# Βήμα 7: Καθαρισμός
git branch -d hotfix/fix-prod-filter
🚨
Hotfix ≠ Feature. Ένα hotfix διορθώνει ΜΟΝΟ αυτό που "καίει". Αν θέλεις να κάνεις και άλλες αλλαγές, φτιάχνεις feature branch ξεχωριστά.

07 Conventional Commits — Η Γλώσσα των Commits

Μια κοινή σύμβαση ώστε όλοι να καταλαβαίνουν τι άλλαξε, από ποιον, και γιατί.

🤔 Γιατί σημαντικό;

Φαντάσου να ανοίγεις το git log 3 μήνες μετά. Ποιο είναι πιο χρήσιμο;

❌ Χωρίς σύμβαση
changes
updated stuff
fix
final version
FINAL v2
aaa
✅ Με Conventional Commits
feat(etl): add daily sales aggregation
fix(sql): correct date filter in query
chore(dsx): export updated job config
docs: update ETL pipeline readme
fix(etl): hotfix filter bug in prod
Prefix Ελληνικά Πότε το χρησιμοποιείς Παράδειγμα Επιτρέπεται σε
feat Νέα λειτουργία Πρόσθεσες κάτι καινούριο feat(etl): add sales transformation feature
fix Διόρθωση Διόρθωσες κάτι που δεν δούλευε fix(sql): correct aggregation logic featurereleasehotfix
chore Τακτοποίηση Δεν άλλαξες λογική — μόνο δομή/config chore(dsx): export updated job config featurereleasehotfix
docs Τεκμηρίωση Ενημέρωσες README ή σχόλια docs: update pipeline documentation featurerelease
refactor Αναδιοργάνωση Ίδια λογική, καλύτερος κώδικας refactor(sql): simplify join logic feature
revert Αναίρεση Αναιρείς ένα προηγούμενο commit revert: revert "feat: add filter" featurereleasehotfix
test Δοκιμές Πρόσθεσες ή ενημέρωσες tests test(etl): add unit test for sales aggregation feature

📐 Η Δομή ενός Commit Message

# Βασική μορφή:
type(scope): σύντομη περιγραφή στα αγγλικά

# Παραδείγματα:
feat(etl): add daily sales aggregation job
fix(sql): correct date filter for EU region
chore(dsx): export sales_pipeline job config
feat(etl/customers): add customer segmentation logic
fix(prod): hotfix null values in revenue column
test(etl): add unit test for sales aggregation
💡
Το scope (αυτό στις παρενθέσεις) είναι προαιρετικό αλλά πολύ χρήσιμο. Δείχνει ποιο κομμάτι του κώδικα αγγίξατε — π.χ. etl, sql, dsx.

08 Τι είναι το Pull Request (PR);

Το βήμα που διασφαλίζει ότι κανείς δεν βάζει κώδικα στο develop χωρίς να το δει κάποιος άλλος πρώτα.

🤔 Με απλά λόγια

Ένα Pull Request είναι μια επίσημη αίτηση να ενωθεί ο κώδικάς σου με κάποιο κεντρικό branch. Δεν κάνεις merge μόνος σου — ζητάς από την ομάδα να κοιτάξει τι έγραψες, να σχολιάσει, και να εγκρίνει. Γίνεται μέσα στο GitHub ή GitLab, στο browser.

1️⃣

Push το branch σου

Ανεβάζεις το feature branch στο remote με git push origin feature/xxx

2️⃣

Άνοιξε PR στο UI

Στο GitHub/GitLab πατάς "New Pull Request", επιλέγεις από feature/xxx προς develop

3️⃣

Code Review

Συνάδελφος κοιτάει τον κώδικα, αφήνει σχόλια. Διορθώνεις αν χρειαστεί και κάνεις push ξανά — το PR ενημερώνεται αυτόματα.

4️⃣

Approve & Merge

Μετά την έγκριση, πατάς "Merge Pull Request". Ο κώδικας μπαίνει στο develop. Το feature branch μπορεί να διαγραφεί.

💡
Καλή πρακτική για PR descriptions: Γράψε τι αλλάζει, γιατί, και πώς να το δοκιμάσεις. Ένα καλό PR description εξοικονομεί χρόνο στον reviewer και επιταχύνει την έγκριση.
⚠️
Ποτέ μην κάνεις merge το δικό σου PR χωρίς review — ακόμα και αν είσαι σίγουρος ότι είναι σωστό. Το review δεν είναι μόνο για bugs, είναι και για να ξέρει η ομάδα τι μπήκε στον κώδικα.

09 Ο Κύκλος Ζωής ενός Feature

Από τη στιγμή που παίρνεις ένα task μέχρι να βγει live στην παραγωγή — το πλήρες timeline.

📋

Παίρνεις το Task

Από Jira, Asana, ή το team board. Διαβάζεις τι ζητάει, κατανοείς τι πρέπει να αλλάξει στον κώδικα.

Branch: ακόμα στο develop
🌿

Δημιουργείς Feature Branch

git checkout -b feature/my-task — Απομονώνεσαι από την υπόλοιπη ομάδα. Γράφεις κώδικα, κάνεις commits.

feature/my-task
🔍

Pull Request & Code Review

Push το branch, ανοίγεις PR στο GitHub/GitLab. Συνάδελφος κάνει review. Διορθώνεις τυχόν παρατηρήσεις.

feature → develop (μέσω PR)
🔀

Merge στο Develop

Εγκρίθηκε το PR. Ο κώδικάς σου μπαίνει στο develop μαζί με τα features άλλων developers. Διαγράφεις το feature branch.

develop
🧪

Release Branch & UAT

Δημιουργείται release/v1.x από το develop. Πάει για UAT testing. Αν βρεθούν bugs, διορθώνονται εδώ.

release/v1.x → UAT
🚀

Production — Live! 🎉

UAT έδωσε OK. Merge στο main, tag της έκδοσης, back-merge στο develop. Ο κώδικάς σου είναι τώρα live.

release/v1.x → main + develop
⏱️
Τυπικό timeline: Feature branch → 1-5 μέρες ανάπτυξη → PR review 1-2 μέρες → UAT 2-5 μέρες → Production. Ο χρόνος ποικίλλει ανά ομάδα, αλλά η ροή παραμένει πάντα η ίδια.

🏢 Παράδειγμα: 3 Teams — Πραγματικό Σενάριο

Πώς δουλεύουν παράλληλα 3 διαφορετικά teams και οδηγούν τον κώδικα στην παραγωγή χωρίς να "συγκρουστούν".

1️⃣
Teams δουλεύουν παράλληλα — ο καθένας στο δικό του branch, ανεξάρτητα από τους άλλους.
2️⃣
Sync συχνά — Team B & C τραβούν το develop μετά από κάθε merge για να αποφύγουν μεγάλα conflicts.
3️⃣
Release μετά από όλα τα merges — το release/v1.0 δημιουργείται μόλις και τα 3 teams έχουν κάνει merge στο develop.

🚀 Σενάριο: Release ενώ άλλα 2 Teams συνεχίζουν

Το Team A έχει ήδη κάνει merge και ο κώδικάς του πάει στην παραγωγή. Τα Teams B & C συνεχίζουν να δουλεύουν ταυτόχρονα στο develop — ανεπηρέαστα από το release.

🔑
Release ≠ όλα τα features — Το v1.0 περιέχει μόνο ό,τι έχει κάνει merge στο develop. Teams B & C θα μπουν στο v1.1.
⚙️
Τα B & C δεν σταματούν — Συνεχίζουν να δουλεύουν ανεπηρέαστα. Το release δεν τους αγγίζει.
🔄
Back-merge στα B & C — Μετά το deployment, το bugfix του UAT πηγαίνει πίσω στο develop και τα B & C το παίρνουν με sync.

10 Κανόνες & Κοινά Λάθη

Κάθε κανόνας αντιστοιχεί σε ένα πραγματικό λάθος που γίνεται στην πράξη. Εδώ έχεις και τον κανόνα και τη λύση αν τον παραβείς.

01

🚫 Ποτέ commit απευθείας στο main

Το main = παραγωγή. Κάθε αλλαγή πρέπει να περάσει από review και testing. Ακόμα και αν είσαι ο μόνος developer.

✅ Λύση: Πάντα git checkout -b feature/xxx πριν γράψεις οτιδήποτε.

02

🚫 Ποτέ commit απευθείας στο develop

Το develop είναι integration branch. Αλλαγές μπαίνουν μόνο μέσω Pull Requests από feature/release/hotfix branches.

✅ Λύση: Ανοίγεις feature branch, κάνεις PR, περιμένεις review.

03

⚠️ Πάντα back-merge από release/hotfix

Μετά από κάθε release ή hotfix, κάνε merge και στο develop. Αλλιώς τα bugfixes θα χαθούν και θα ξαναεμφανιστούν!

✅ Λύση: Κάνε το back-merge αμέσως μετά το merge στο main — μην το αφήνεις για αργότερα.

04

🏷️ Πάντα tag στο main μετά από release

Τα tags είναι σαν "φωτογραφίες" της παραγωγής. Σε βοηθούν να γυρίσεις σε οποιοδήποτε release αν χρειαστεί.

✅ Λύση: git tag -a v1.x -m "..." αμέσως μετά το merge στο main.

05

🔄 Sync συχνά με το develop

Ανοίγεις branch, δουλεύεις για εβδομάδες χωρίς sync. Αποτέλεσμα: τεράστια conflicts όταν έρθει η ώρα του merge.

✅ Λύση: git merge develop στο feature branch σου κάθε 1-2 μέρες.

06

📝 Descriptive commit messages

Χρησιμοποίησε conventional commits. Ένα "fix stuff" δεν λέει τίποτα σε κανέναν — ούτε σε σένα 3 μήνες μετά.

✅ Λύση: feat(etl): add sales logic αντί για changes.

07

💥 git push --force

Το force push ξεγράφει ιστορία στο remote. Αν το κάνεις σε shared branch, σβήνεις δουλειά συναδέλφων.

✅ Λύση: Ποτέ --force σε develop/main/release. Μόνο σε personal feature branches αν είναι απαραίτητο.

08

🔑 Commit passwords ή API keys

Ανεβάζεις αρχείο config με credentials. Μόλις πάει στο remote, είναι εκτεθειμένο — ακόμα και αν το διαγράψεις μετά.

✅ Λύση: Χρησιμοποίησε .gitignore για config files. Αν ανέβηκε ήδη, άλλαξε αμέσως τα credentials.

09

🚧 Νέα features στο release branch

Ενώ το release είναι ανοιχτό για UAT, προσθέτεις νέα λειτουργικότητα αντί για μόνο bugfixes.

✅ Λύση: Το release branch δέχεται μόνο fix/docs/chore. Νέο feature → επόμενο release.

⚡ Quick Reference — Τι κάνω αν...

Ξεκινάω νέα εργασία:
develop → feature/xxx → PR → develop
Ετοιμάζω release:
develop → release/vX.Y → UAT → main+develop
Βρήκα bug στην παραγωγή:
main → hotfix/xxx → main+develop+release
Υπάρχει conflict:
pull develop → merge develop στο feature → resolve → push
Ξέχασα back-merge:
Κάνε το τώρα — checkout develop, merge release/hotfix, push
Θέλω να δω την ιστορία:
git log --oneline --graph --all

🛠️ Χρήσιμες Επιπλέον Εντολές

Handy Git Commands
# Δες όλα τα branches (local + remote)
git branch -a

# Δες το log γραφικά
git log --oneline --graph --all

# Δες τι αλλαγές έχεις κάνει
git status
git diff

# Αναίρεσε αλλαγές σε ένα αρχείο (πριν commit)
git checkout -- filename.sql

# Δες ποια tags υπάρχουν (releases)
git tag -l

# Ποιος άλλαξε τι σε ένα αρχείο;
git blame sales_etl.sql

# Γύρνα σε μια προηγούμενη έκδοση (tag)
git checkout v1.0
